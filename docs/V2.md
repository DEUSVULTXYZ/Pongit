# PONGIT V2

## Implemented behaviour

Classic and Chaos use separate ranked queues and onchain ratings. Friendly challenges do not alter either ladder. Every join signs mode, ranked status and rules version 2, as well as both accounts, session key, room, deadline and nonce. Tournaments remain Classic ranked.

GameV2, MarketV2, a fresh Vault and TournamentsV2 are immutable deployments. GameV2 creates a stateless, immutable EloFormulaV2 for its existing PRBMath calculation. Market binding and vault modules are sealed before the first match. Input limits are copied into each match. A ranked result must finalize before its players start another match; the keeper finalizes it independently of financial settlement.

Chaos accumulates actual accepted MON costs per side, never seed liquidity. Claims never reduce this counter. Before 0.002 MON there is no handicap. A favourite above 60% loses height linearly, up to 25% at 100% concentration (96 → 72 units). Integer basis-point rounding is conservative. After each nonfinal point the keeper starts a full three-second break on the match clock. Bets close for its final two blocks. Resume reads paid pressure once and freezes both paddle heights for the next rally. Late catch-up stops at the break, never simulating future rallies with old sizes.

## Accounts, challenges and privacy

Mera's existing default wallet PRF salt is unchanged. A separate SHA-256 namespace, `pongit.xyz/notebook/v1`, feeds a distinct PRF evaluation restricted to the connected credential. HKDF derives a nonextractable AES-GCM key. Each save uses a fresh random 96-bit IV and account-bound authenticated data. Only ciphertext, IV, revision and a technical update timestamp reach PostgreSQL. Keys and decoded notes stay in memory and close on lock, disconnect or account change. JavaScript strings are garbage-collected; a browser extension or compromised page that can read live memory remains outside this protection.

The app session is a separate, signed, chain-and-contract-bound challenge with a single-use nonce. Its one-hour cookie is HttpOnly, SameSite Strict and Secure on HTTPS. The database stores the token hash. This session only authorizes profiles, invitations and encrypted notebook access, never a transaction or withdrawal. Notebook updates compare revisions; a conflict preserves local edits until the user chooses to reload the saved copy.

Public profiles are optional, with a unique lowercase handle and twelve preset geometric avatars. They can be removed; public chain results remain. Invitations expire after ten minutes, bind friendly/ranked and mode, respect blocks and persistent creation quotas. Addressed links enforce the recipient. Open-link acceptance uses a row lock plus the matchmaking advisory lock so exactly one recipient is reserved. The inbox refreshes while connected and shows a notification outside the Rivals page. Submitted match transactions retain their true receipt state and cannot be falsely cancelled.

## Rendering and transport

The site keeps Michroma with its bundled licence. Precomputed neon logos and short CSS transitions avoid adding a 3D runtime to the arena. Reduced-motion preferences disable the visual effects. Sounds start muted. Personal VICTORY/DEFEAT screens follow an observed live-to-confirmed-result transition only; historical loads and reconnections do not replay a celebration. Spectators get a neutral winner notice. Controls remain available to skip the effect, rematch through a challenge, open the replay or choose another opponent.

The browser predicts rendering while Solidity remains authoritative. The existing monotonic frame filter and hold at unresolved paddle impacts remain. Individual paddle heights and the intermission are mirrored in TypeScript. Chain inclusion delay still exists; prediction does not remove it.

`web/lib/transport.ts` separates snapshots, the clock, notifications and settled results. The active adapter is Monad. Interlude is not selectable or represented as integrated. Before adopting the hosted operator, validate its SDK, session-key persistence, delegated-clock semantics, expiry and failure recovery, and redeploy compatible financial/result contracts. A live delegated value must never be treated as a settled Monad result. The operator's current [limits documentation](https://interludelayer.xyz/docs/limits) remains a required migration review; no hosted Interlude node or live integration is part of this release.

## Versioning and operations

References use deployment-qualified IDs (`v1:12`, `v2:1`) in Envio and private notes. Active API numeric IDs are always scoped by `/config`; legacy requests use `/legacy/`. V1 balances, claims, withdrawals and replays remain separately accessible from Archive. There is no automatic fund transfer. Classic ELO is inherited from the drained V1 game; Chaos starts at 1000.

The relayer retains its original deployment fingerprint and signing identity. V2 registers an additional manifest and labels older untagged jobs V1 without replacing signed bytes, receipts or nonces. Only one process can hold the signing advisory lock. Historical calls are restricted to claims, refunds and withdrawals. The deployment operator helper uses the same lock, persistent signed journal and balance accounting for funding transfers. It requires the relayer to be stopped and all jobs drained; interrupted signed transfers remain recoverable by their exact bytes.

At the owner’s explicit request on September 6, the daily spending ceiling is disabled (`RELAYER_DAILY_BUDGET_MON=0`). Nonzero values can restore an optional ceiling. Balance reservations, the gas-price ceiling, per-account quotas and solvency checks still apply.

Envio uses a separate `pong_indexer_v2_47dba35e` database with the existing restricted indexer role. It indexes both contract versions into qualified entities, including HandicapSet events and full replay states. The original indexer database is retained. Backups include both indexer databases and the relayer journal.
